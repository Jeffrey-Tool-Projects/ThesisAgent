- **#5** [UNVERIFIED] The first release after U-20260925-01 builds cold (the cache key's paths changed). On the release after that, check the Nuitka log line `Compiled N C files using clcache with H cache hits` and the job time: if the build is warm, replace the expected ~5–10 min in `docs/releases.md` and the README (all 14 languages) with the measured value. If hits stay low, clcache's default 1 GiB size limit (`MaximumCacheSize` in Nuitka's inline `clcache/caching.py`) may be evicting objects. Measured so far (job step times from the public API, 2026-11-20): 2026-10-08 restored no cache and compiled for 97 min, 2026-10-11 restored the cache saved three days before and still compiled for 100 min, so hits were low. 2026-11-19 (v0.1.25) restored no cache (the 2026-10-11 one had passed the 7-day eviction), compiled for 115 min of the 120 min cap, and saved a 57 MB cache (zstd-compressed, read from the job log), so the save step does write the cache. Its log line reads `Compiled 4191 C files using clcache with 0 cache hits and 4191 cache misses`, as expected for a build with no cache. The real test is the next release within 7 days, which restores this cache. If its hits are again near 0, suspect what the workflow leaves unpinned: `pip install nuitka` and Python `3.12` take the newest release each time, and a new Nuitka or Python patch changes the generated C or the headers, so clcache misses every file. Pinning both and putting them in the cache key would then be the fix. The hit count itself needs the signed-in job log. From U-20261120-03 the compile runs with 4 jobs. The first such build, 2026-11-20 (v0.1.26, job 136166163111), compiled for 61 min against 115 min the day before, with no fallback to 2 jobs. Its cache step took under a minute, so whether it restored the 57 MB cache and how many hits it got comes from the job log, read with `gh run view --log`: `Cache not found for input keys: nuitka-Windows-…`, and `0 cache hits and 4191 cache misses`. Cause found: the repository's Actions cache store (10 GB) was full of `setup-python` pip caches of about 400 MB each, keyed on `pyproject.toml`, so every version bump added new ones and the 54 MB Nuitka cache was evicted within hours. U-20261120-05 keys the CI pip cache on the lock and drops the Nuitka job's pip cache. On 2026-11-21 the store still held 17.3 GB: with setup-python's `cache: pip`, `dev`, each PR merge ref and each Dependabot branch saved their own six entries of about 450 MB, and the 54 MB Nuitka cache saved by v0.1.26 had only 2 GB of less recently used caches ahead of it. U-20261121-01 saves the CI pip cache from `main` only. The old per-branch entries expire 7 days after their last use. Check on the next release that `Cache restored from key: nuitka-Windows-…` appears and how many hits it gets, before pinning Nuitka or Python. If the cache is gone again, look at `gh cache list -L 100` first.
